# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

Multi-file project for accessibility-oriented multilingual text analytics. There is no test suite and no build step.

**Core pipeline:**

- `accessible_text_analyst.ipynb` — the entire NLP pipeline (42 cells: 21 code + 21 markdown). The notebook narrative and `print()` outputs are in **Russian** and were intentionally written without color, emoji, or pseudographic art so they read cleanly through NVDA/JAWS screen readers. The notebook itself emits two accessibility artefacts (`accessible_text.html`, `accessible_text.docx`) where every paragraph and every foreign-language sentence carries its own `lang` attribute so screen readers and TTS engines switch voice automatically.
- `generate_report.py` — standalone post-processor that turns the executed notebook into a single accessible HTML file (`analysis_report.html`), written into `export_results/<project_dir>/` alongside the notebook artefacts. The script reads `source_file` from `config.json` (or `config.ini`) and applies the same slugify rules as `cell_corpus` to pick the project subdirectory. It wraps foreign-language fragments in `<span lang="target_lang">` and **always** wraps technical English fragments (POS tags, NER labels, spaCy/HF model names, ASCII filenames) in `<span lang="en">` regardless of corpus language.
- `generate_md.py` — converts the generated `analysis_report.html` to `gemini_notebook_report.md` for Gemini Notebook (Google renamed NotebookLM to Gemini Notebook in July 2026; the artefact was `notebooklm_report.md` before v1.5.0). Reads from and writes to the same `export_results/<project_dir>/`. Strips accessibility spans because Gemini Notebook does not consume them.

**Optional shamanic post-processing layer** (writes into `export_results/<project_dir>/audio_scripts/`):

- `shamanic_pipeline.py` — non-LLM ritual generator. Reads the notebook's CSV/JSON exports and produces up to five text artefacts: `oracle_script.txt` (theses with TTS pauses), `lore_fragments/intercepted_log_T*_P*.txt` (per-paragraph lore tagged by topic), `raw_roots_chant.txt` (TF-IDF keyword chant), `prophecies.txt` (template-driven prophecies woven from NER entities + longest paragraphs), and — only when the optional `sentiment.csv` exists — `emotional_undertow.txt` (per-paragraph mood tide + balance). All strings come from `shamanic_locale.py`.
- `shamanic_ai.py` — LLM-driven ritual narrators (`Katla`, `Vieno`, `Lumi`, `Sami`). Calls OpenAI (`gpt-4o`) with prompts in English but instructs the model to output in the corpus's detected language via `LANGUAGE_NAMES[lang]`. Reads `OPENAI_API_KEY` from `golden_key.env` (gitignored, matches `*.env`). Lumi's fallback strings for missing Katla/Vieno artefacts are localized — see `lumi.fallback.katla` and `lumi.fallback.vieno` in the bundle.
- `shamanic_voice.py` — **optional, third-party + paid.** Run-once audio dispatcher: reads the four `shamanic_ai.py` artefacts (`katla_entity_monologue.txt` / `vieno_echoes_chant.txt` / `lumi_final_report.txt` / `sami_energetic_spark.txt`, hardcoded English names matching `shamanic_ai.py`), synthesizes each into a sibling `.mp3` via the ElevenLabs `eleven_multilingual_v2` model, logs success/failure to the console, and exits — no Discord, no server, no interactive loop (this replaced the earlier `lumi_dispatcher.py` bot skeleton). Reads `ELEVENLABS_API_KEY` from `golden_key.env` and a `voices` mapping (`katla`/`vieno`/`lumi`/`sami` → ElevenLabs voice ID) from `config.json`/`.ini`. Console strings are localized via `t(UI_LANG, "dispatcher.*")` in `dictionaries/{lang}/reports.yaml` (operator-facing console script, so it lives with `generate_report`/`generate_md`, **not** in `shamanic.yaml`). No new pip deps — `requests` + `python-dotenv` were already required.
- `shamanic_locale.py` — i18n loader for YAML dictionaries under `dictionaries/{lang}/*.yaml`. Public surface: `t(lang, key, **kwargs)` flattens nested YAML keys to dotted form (`prophecy.fallback.loc`) and applies `.format()`; bundles are loaded lazily via `@lru_cache(maxsize=8)` with per-key fallback to `en`. `get_ui_lang(default='en')` reads the `ui_lang` key from `config.json`/`.ini` and normalizes it against `LANGUAGE_NAMES` — empty/unknown falls back to `default`. `detect_corpus_lang(export_dir)` reads the `<html lang="...">` attribute from `accessible_text.html` (fallback: lingua over the first ~30 sentences from `sentences.csv`). `LANGUAGE_NAMES` (`pl/en/ru/fi/is/it` → human names used in LLM prompts). PyYAML is a hard dependency from v1.1. **Use `lang`-anything as placeholder in YAML strings carefully: the `t()` signature already takes `lang` as a positional, so a kwarg named `lang` collides — name UI placeholders `{language}` instead (already done for `info_detected_lang` / `info_target_lang`).**

```bash
# Install dependencies (Python 3.10+ assumed; .venv is in .gitignore)
pip install -r requirements.txt

# spaCy models are NOT in requirements.txt — install the *_lg models for each language you need.
# The notebook's MODEL_BY_LANG hardcodes _lg variants because KMeans topics + NER quality depend on word vectors.

python -m spacy download ru_core_news_lg
python -m spacy download en_core_web_lg
python -m spacy download it_core_news_lg

# Icelandic (is) intentionally falls back to spacy.blank("is") — no model exists.

# Optional Finnish morphology upgrade: uncomment `omorfi` in requirements.txt,

# Run the notebook end-to-end
jupyter notebook accessible_text_analyst.ipynb

# After executing the notebook (so its cells contain outputs), generate the HTML report:
python generate_report.py
```

### Editing notebook cells (jupytext)

The notebook is **paired** with `accessible_text_analyst.py` (`py:percent` format) via
jupytext — this replaces the old `.claude_patches/` one-shot OLD→NEW patch scripts.
The pairing is recorded in the notebook's own metadata (`metadata.jupytext.formats =
"ipynb,py:percent"`), so it survives clone and nbstripout. Both files are committed:
the `.py` gives clean reviewable diffs, the `.ipynb` is the runnable artefact (outputs
stripped by nbstripout on commit). Run `jupytext --sync` before committing so they
don't drift.

```bash
# Regenerate the .py from the notebook (do this first if the .py is missing/stale,
# e.g. after a fresh clone or after editing the notebook in Jupyter):
jupytext --sync accessible_text_analyst.ipynb

# Edit accessible_text_analyst.py directly — each cell is a navigable block marked
#   # %% tags=["cell_para"] id="cell_para"      (code)
#   # %% [markdown] tags=["md_intro"] id="md_intro"
# then push the edits back into the .ipynb:
jupytext --sync accessible_text_analyst.py
```

`jupytext --sync` takes the more-recently-modified file as source and updates the other.
It **preserves outputs** of cells whose source is unchanged and keeps outputs of edited
cells too (it does not re-execute) — so after editing, **re-run the notebook** before
`generate_report.py`, which reads outputs from the `.ipynb`. Every cell carries a stable
anchor in BOTH `metadata.id` and `metadata.tags` (logical names: `cell_corpus`,
`cell_langdet`, …, `cell_qa_rag`; markdown: `md_intro`, …). nbstripout (v0.9.1, active via
`.git/info/attributes`) preserves `metadata.jupytext`, `tags`, and `metadata.id` — it only
strips outputs/execution_count. Do **not** put logical names in the top-level cell `id`
field; it gets renumbered to integers by some clients.

A **local** `.git/hooks/pre-commit` automates the sync: when either paired file is staged
it runs `jupytext --sync` (via `.venv/Scripts/python.exe`) and re-stages both, so they
can't drift. The hook is not committed (it lives in `.git/`); reinstall it after a fresh
clone, or use a committed `.pre-commit-config.yaml` for portability. nbstripout still
strips outputs from the `.ipynb` blob independently.

`requirements.txt` lists `nbstripout` — if it has been activated in the local git config, notebook outputs are stripped on commit. `generate_report.py` reads outputs from the `.ipynb` file directly, so the report must be regenerated from a freshly-executed notebook (don't commit-then-report).

## Pipeline architecture (notebook)

The notebook's 42 cells (21 code + 21 markdown) are a linear, stateful pipeline — every cell reuses globals from the previous ones (`corpus`, `LANG`, `LANG_DETECTOR`, `nlp`, `stop_words`, `docs`, `para_lemmas`, `df_para`, `df_sent`, `para_sentences`, `para_langs`, `sent_langs`, etc.). **Do not reorder cells or run them out of order.** The flow:

1. **`cell_corpus`** — only user-facing input: set `SOURCE_FILE` to a `.pdf` / `.txt` / `.docx` / `.html` / image path or an `http(s)://` URL. Empty string → built-in `FALLBACK_CORPUS`. Loaders strip repeated PDF headers/footers (`strip_repeated_headers` with `_STRUCTURAL_PATTERNS` protection for scene/act/chapter markers in six languages), de-hyphenate, and for HTML/URL run a BeautifulSoup main-content heuristic (`<main>`/`<article>` → id/class containing `content|article|post|story`). `CUSTOM_PATTERNS` is a list of regexes pre-stripped from txt/docx/html. **Config loading** accepts both `config.json` and `config.ini` (content is JSON in either case — the `.ini` extension is a usability concession for Windows users for whom `.json` has no default handler). Image inputs (`.png`/`.jpg`/`.jpeg`/`.tif`/`.tiff`/`.bmp`/`.webp`) and scan-only PDFs fall back to `pypdfium2` + `easyocr` (`_pdf_ocr_pages`, `load_image`). The OCR dependency block is commented out in `requirements.txt` by default — uncomment for OCR.
2. **`cell_langdet`** — uses `lingua-language-detector` (replaced `langdetect` for higher per-fragment accuracy). Determines the dominant corpus language as `LANG`, plus exposes globals `LANG_DETECTOR` and `detect_lang(text)` consumed later by `cell_para` and `cell_export`. Supported set: `{en, pl, ru, it, fi, is}` (`SUPPORTED_LANGS`). Output keeps the format `Выбран язык: <name> (<code>)` so `generate_report.py` can detect the target language.
3. **`cell_model`** — model loading is gated by `get_nlp(lang)` decorated with `functools.lru_cache(maxsize=2)` — at most two spaCy models live in RAM at once, the LRU is evicted on demand. `nlp = get_nlp(LANG)` is loaded eagerly for the dominant language; `MODEL_BY_LANG` provides the `_lg` model names. Icelandic still uses `spacy.blank("is")` + Hugging Face IceBERT vectors + `mideind/icelandic-ner-MIM-GOLD-22` (these require `transformers` + `torch`, which are commented out in `requirements.txt` by default — uncomment for `is` support). The legacy alias `load_nlp_model` is kept. **Optional Finnish morphology upgrade:** when the `omorfi` package (pure-Python since 0.10, dep `pyhfst`; commented out in `requirements.txt`, mirroring the OCR/Icelandic/sentiment pattern) is importable AND its FST automata are present (`omorfi-download` unpacks ~130 MB of `*.hfst` files into the CWD; `OMORFI_MODEL_CANDIDATES` probes `omorfi_recased.describe.hfst` first, then `omorfi.describe.hfst`; `*.hfst` is gitignored), `_build_finnish_omorfi()` appends an `omorfi_lemmas` component (registered via `Language.has_factory` guard — a bare re-registration can die with `OSError: could not get source code` outside IPython) that overrides `token.lemma_` and `token.morph` with dictionary analyses. The pip omorfi has no contextual disambiguation, so candidates are filtered by the spaCy tagger's UPOS and the lowest-weight match wins; **no UPOS match → token untouched** (conservative: dictionary and tagger disagree, trust spaCy). Compound lemmas arrive in parts and are joined with inner hyphens dropped unless the surface form itself is hyphenated (`trolli`+`tehdas` → `trollitehdas`, but `Itä-Suomi` keeps its hyphen). Known imperfection: same-UPOS homonyms resolve by weight (`sinä` → `se`, the essive-of-`se` reading; harmless — pronouns are stopwords). Missing package / missing automata / load failure → one Russian info line and the unchanged model (soft degradation). Measured on a real Whisper transcript: 100% coverage, ~1 ms/word (plus a 64k-entry `lru_cache` per surface form), and it fixes exactly the garbage lemmas `fi_core_news_lg` produces (`kytköksistä` → `kytkös`, not *kytköks*; `pistät` → `pistää`, not *pisttää*). `generate_report.py` was extended to match: `_SPACY_PIPELINE_COMPONENTS` gained `omorfi_lemmas|omorfi-download|omorfi|pyhfst` (order matters — `omorfi-download` before bare `omorfi`), and the ASCII-filename EN-hardcode pattern now accepts the `.hfst` extension and multi-dot stems (`omorfi_recased.describe.hfst`).
4. **`cell_pl_corrector`** — regex-only normalization (no morphology). Runs across all languages: collapses doubled words/whitespace; for `pl`/`ru`/`en` normalizes spaced abbreviations (`m. in.` → `m.in.`, `т. е.` → `т.е.`, `e. g.` → `e.g.`).
5. **`cell_tok` → `cell_stop` → `cell_lemma` → `cell_pos` → `cell_ner`** — standard spaCy steps; `stop_words` comes from the loaded model.
6. **`cell_bow`, `cell_tfidf`** — sklearn `CountVectorizer`/`TfidfVectorizer`; auto-query for TF-IDF search is built from top corpus terms so cosine similarity is guaranteed > 0.
7. **`cell_para`** — joins the whole corpus, re-splits via spaCy `sents`, then groups sentences into 3–6-sentence "paragraphs". `para_lemmas`, `df_para`, `df_sent` feed the rest. Builds three additional globals consumed by `cell_export`: `para_sentences` (list of sentence-lists per paragraph), `para_langs` (ISO code per paragraph via lingua), `sent_langs` (ISO code per sentence). A local `_safe_detect()` falls back to `LANG` for fragments too short for reliable detection.
7a. **`cell_foreign_resegment`** — second pass on `para_sentences` / `sent_langs` to re-segment mixed-language paragraphs. Splits a paragraph at language boundaries so that adjacent sentences in different languages end up in different paragraphs (otherwise a single paragraph in `accessible_text.html` would carry a misleading dominant `lang` attribute, and DOCX `<w:lang>` would inherit it).

   **Known limitation — metalinguistic etymology is out of scope.** The per-fragment `lingua` detection in `cell_para` / `cell_foreign_resegment` only tags fragments written in a foreign *script* (actual Greek letters, Latin inside a Cyrillic text). It deliberately does **not** detect loanword *origin markers* (`греч.`, `łac.`, `z niemieckiego`, `имеет греческое происхождение`), does not link such a marker to the borrowed word, and does not handle foreign words *transliterated into the host script* (`фразис`, `логос` in a Russian text — Cyrillic, not Greek). This was evaluated and rejected: marker forms are an open class (abbreviation / inflected adjective / prepositional phrase / full verbal description — relation extraction, not regex); the etymology has no delimitable "block" to strip because it is woven into ordinary prose (e.g. *«Слово фразеология имеет греческое происхождение: фразис означает …»*); and tagging a transliterated word with the donor language's ISO code would *mislead* the screen reader (NVDA reading Cyrillic `фразис` with a Greek voice is worse than the Russian default). Reliable detection would need a trained relation-extraction model or an LLM — disproportionate to an otherwise deterministic, offline pipeline. The tractable subset (fragments in an actual foreign script) is already covered here. See `release_notes.md` (v1.4.0).
7b. **`cell_multilang_pass`** — per-language diagnostic re-run. After paragraphs are tagged with `para_langs`, this cell loads each non-dominant language's spaCy model on demand (going through `get_nlp()` and the same LRU cache) and re-runs tokenization / stopword filtering / lemmatization / POS / NER over the paragraphs of *that* language. Used to produce per-language POS tables and lemma listings in the report; without this, e.g. Finnish sentences inside a Polish-dominant corpus get tagged by the Polish model and produce nonsense lemmas.
8. **`cell_keywords`** (TF-IDF n-grams 1–3 over paragraphs) → **`cell_theses`** (best sentence per paragraph by TF-IDF sum, written to a corpus-language-localized filename — `t(LANG, "theses.filename")` from `dictionaries/{lang}/artifacts.yaml`: `tezy.txt` / `theses.txt` / `тезисы.txt` / `teesit.txt` / `tilgátur.txt` / `tesi.txt`) → **`cell_topics`** (KMeans over spaCy paragraph vectors; **silently skipped if model has no vectors**, hence the `_lg` requirement).
8a. **`cell_sentiment`** (optional, off by default) — between `cell_topics` and `cell_export`. Gated by `ENABLE_SENTIMENT`; scores each paragraph and writes raw `sentiment.csv`. See *Sentiment as optional shamanic feed* below. Never shown to the user (excluded from the report). When the flag is off (the default) it prints a one-line skip notice and writes nothing.
9. **`cell_export`** — writes CSV (UTF-8 BOM for Excel) and JSON to `export_results/<project_dir>/`. Also produces two accessibility artefacts:
    - `accessible_text.html` — built with BeautifulSoup; `<html lang="LANG">`, `<p lang="para_langs[i]">` per paragraph, `<span lang="sent_langs[j]">` per sentence inside paragraphs whose sentences disagree.
    - `accessible_text.docx` — built with python-docx; each `Run` has `<w:lang val=... eastAsia=... bidi=...>` set via OOXML using `LANG_TO_LOCALE` (`pl-PL`, `ru-RU`, `en-US`, `it-IT`, `fi-FI`, `is-IS`).
    These replace the previous `чистый_текст_для_аудио.txt` flat file. Both are written wrapped in try/except so missing optional deps (bs4, python-docx) only print a warning instead of failing the whole cell.
10. **`cell_summary`** — single text block aggregating all metrics; this is the screen-reader-friendly "final report". Reports `para_langs` and `sent_langs` distribution and the byte sizes of `accessible_text.html` / `accessible_text.docx`.
11. **`cell_qa_rag`** — interactive TF-IDF retrieval. Excluded from the HTML report by ID (see below).

**Sentiment analysis is back as an opt-in shamanic feed (`cell_sentiment`, off by default).** History: the original `cell_sentiment` (Hugging Face `cardiffnlp/twitter-xlm-roberta-base-sentiment`, 3-class negative/neutral/positive, per-*document* with a 40% confidence floor and an aggregate over reliable pages) was dropped in commit `e5ae27c`. The real cause was operational, not conceptual: the weights downloaded fine, but the cell crashed building the tokenizer. The model ships only `sentencepiece.bpe.model` (no `tokenizer.json`), so `transformers` 5.x must build the XLM-RoBERTa tokenizer from the SentencePiece model — which needs **three** extra packages at once: `sentencepiece` + `protobuf` (without them: `Error parsing line b'\x0e' ...`) **and** `tiktoken` (without it: `tiktoken is required to read a tiktoken file`). Both error messages are real, distinct missing-dependency signals — neither is a red herring; the original crash hit one of them. The reanimated version (see *Sentiment as optional shamanic feed* below) keeps the same model but changes everything around it: it is gated by `config.json`'s `enable_sentiment` (default `false`) and a commented `transformers`+`torch`+`sentencepiece`+`protobuf`+`tiktoken` block in `requirements.txt`; it scores **paragraphs** (`para_id`), not documents; it never prints a verdict to the screen-reader-facing report (excluded from `generate_report.py`); and it writes **raw, unfiltered** rows to `sentiment.csv` (no confidence floor, no outlier exclusion — that filtering belonged to the old *presentation* path; the shaman now takes everything). On load failure (incl. the `tiktoken` error) there is **no English-model fallback** — the cell silently skips and the rest of the pipeline is unchanged. `cell_sentiment` reuses `_silence_hf_progress()` so progress bars / unauthenticated-request warnings stay out of stdout. The tweet-trained model is still noisy on long-form prose, but that is acceptable here because the output is *creative feed* for a ritual, never a verdict shown to the user.

## Shamanic post-processing layer

The shamanic modules are an **optional** layer that runs *after* the notebook has been executed (i.e. after `export_results/<project>/` contains the CSV/JSON artefacts). They are not part of the analysis pipeline — they consume its output to produce text artefacts intended for TTS narration. Three stages (the third is independent of and optional after the first two):

1. **`shamanic_pipeline.py`** — pure-Python, no LLM, no network. Reads `theses.csv`, `keywords_tfidf.csv`, `entities.csv`, `paragraphs.csv`, `paragraphs_with_topics.csv`, and the optional `sentiment.csv`. Produces up to five artefacts under `audio_scripts/`. Idempotent and offline. Writes one ritual artefact per ritual: `ritual_oracle`, `ritual_lore_fragments`, `ritual_raw_roots`, `ritual_etymological_prophesy`, and `ritual_emotional_undertow` (reads `sentiment.csv` → `emotional_undertow.txt`: a mood "tide" of localized words `undertow.mood_{negative,neutral,positive}` per paragraph plus a balance summary; **silently skipped if `sentiment.csv` is absent**, i.e. sentiment disabled or failed). The prophecy generator picks top NER entities by `LOC`/`GPE`, `PERSON`/`PER`, `ORG` and round-robins through four localized templates (`prophecy.templates`). For Finnish and Icelandic, templates use nominal-prefix forms (`paikan {loc}`, `staðnum {loc}`, `hahmon {per} kautta`) because spaCy returns entities in declined form (`Euroopassa`, `Yhdysvaltoihin`, …) and we have no reliable way to re-inflect them back to nominative.
2. **`shamanic_ai.py`** — LLM layer. Calls OpenAI `gpt-4o` four times in sequence: `ritual_entity_transformation` (Katla, monologue from `entities.csv`), `ritual_echoes_of_the_old_world` (Vieno, chant from `topic_keywords.json` + **branch**: if the optional `sentiment.csv` exists and has rows, Vieno builds her song from the keywords + the per-paragraph sentiment as an emotional arc — small corpora (≤ `_SENT_MAX_RAW`=150 paragraphs) get the full raw rows, larger ones are downsampled to ≤ `_SENT_SEGMENTS`=40 ordered segments (dominant mood + mix) so the request fits the 30k-TPM gpt-4o limit (full raw of a 2579-para book is ~32k tokens → 429); otherwise she falls back to the original behavior — keywords + 5 raw sentences from `sentences.csv`. No English-model fallback; absence of `sentiment.csv` = original behavior), `ritual_final_dispatch_lumi` (Lumi, final dispatch — requires `prophecies.txt`, optionally folds in Katla's monologue and Vieno's chant via `_read_artifact_body`; ornament limits come from `lumi_katla_lines` / `lumi_vieno_lines` in `config.json` — `null` or missing key = full content, integer N > 0 = first N non-empty lines), and `ritual_sami_spark` (Sami, energetic synthesis from Lumi's report). All four prompts are in English but instruct the model to output in `LANGUAGE_NAMES[lang]` — this is intentional because English instructions are followed more rigorously, while output language is controlled by an explicit parameter. The two "anchor" Polish folk-song quotes (`SHAMAN_QUOTE_PL`, `LUMI_QUOTE_PL`) are passed with English glosses (`*_GLOSS`) so the model understands them regardless of corpus language; the prompts explicitly forbid the model from reproducing the quotes verbatim. **Lumi's fallback strings** (`lumi.fallback.katla`, `lumi.fallback.vieno`) are localized in `shamanic_locale.py` — when extending, add the fallback for any new language.
3. **`shamanic_voice.py`** — audio dispatcher (optional, **paid + third-party**). Reads the four `shamanic_ai.py` `.txt` artefacts (using the same `_read_body` first-block-to-`\n\n` split as `_read_artifact_body`), POSTs each body to ElevenLabs (`eleven_multilingual_v2`, which auto-detects the spoken language, so no `corpus_lang` is passed), and writes a sibling `.mp3`. Follows the same three-valued contract as the rituals: a voice synthesized → counted; a missing artefact, empty body, or missing voice ID → skipped silently/with a `[SKIP]` line; an HTTP/synthesis error → raised and caught per-voice (one failure does not abort the others). Critical guard raises on a missing `audio_scripts/` dir, plus up-front guards for missing `ELEVENLABS_API_KEY` and missing `voices`. Console output only — it writes no localized text artefact, so it needs no `shamanic.yaml` keys (its `dispatcher.*` keys are in `reports.yaml`).

When adding a new shamanic step that prints to a text artefact: add a localized header key (`yourstep.header`) to all six `dictionaries/{lang}/shamanic.yaml` files, and use `t(corpus_lang, 'yourstep.header')` at write time — never hard-code Polish/English strings in the writer. Multiline headers must use the `|+` block scalar (chomping = keep) so trailing `\n\n` is preserved exactly as the writer expects.

**Failure-handling contract (v1.3.1).** Each `ritual_*` function returns a status and the `__main__` of each module runs the rituals through a per-ritual `try/except` loop so one failure never aborts the others (the rituals are independent — a single faulty export file should not silence the whole layer). The contract is three-valued: **produced** → `return True` after the artefact is written and the `ok_*` line is printed; **legitimately skipped** → `return False` silently when a *conditionally-written* input is simply absent (no error); **failed** → `raise RuntimeError(...)` when an input is present but unusable. The two skip-vs-fail decisions hinge on which exports are guaranteed: `sentences.csv` and `paragraphs.csv` are written by **every** successful run of the notebook's export cell, whereas `theses.csv` / `keywords_tfidf.csv` / `paragraphs_with_topics.csv` / `topic_keywords.json` / `entities.csv` / `sentiment.csv` are written **conditionally** (empty result, no `_lg` vectors, sentiment off). So a missing *conditional* input = `return False` (valid partial pipeline); a missing `paragraphs.csv`/`sentences.csv` = `raise` (the export cell never ran). **One exception:** `ritual_etymological_prophesy` treats `entities.csv` as optional *ornament*, not a gate — its templates fall back to placeholder `loc`/`per`/`org` via `pick()` (and frequently do even when entities exist, if no sampled paragraph carried one), so it produces `prophecies.txt` from `paragraphs.csv` alone (never `return False`s — it only `raise`s if `paragraphs.csv` is missing or yields no usable paragraphs). Two localized message flavors carry this distinction to the operator: `*.err_no_notebook_output` / `*.err_no_export_dir` ("the notebook or its export cell was probably not executed") and `*.err_faulty_input` ("file present but empty/corrupted — something went wrong"). Each module's `__main__` opens with a **critical guard** that raises `pipeline.err_no_notebook_output` (or `ai.err_no_export_dir`) when `paragraphs.csv` / the export dir is missing, then classifies the final message: any failure → `*.done_with_errors`; zero produced but no failure → `*.warn_nothing_produced`; otherwise → `*.done`. This is what stops the misleading `[ZAKOŃCZONO] … wszystkie artefakty gotowe` from printing over an empty `audio_scripts/` (the symptom behind the v1.1.5 fix — there the root cause was a slug mismatch, here the design that let it print silently is closed). In `shamanic_ai.py`, Lumi and Sami still `return False` **silently** when `prophecies.txt` / Lumi's report is absent (the local pipeline simply wasn't run first — not an error), but Vieno now **raises a warning** (`ai.warn_vieno_too_few_sentences`) instead of silently returning when her non-sentiment branch finds fewer than 5 raw sentences. The TTS pause marker in `ritual_oracle` is localized via `oracle.pause` (`[PAUZA 1.5s]` / `[PAUSE 1.5s]` / …) — it is corpus-language, like the headers.

**Two languages, one module.** `corpus_lang` (from `detect_corpus_lang()`) is the *content* language — used for artefact-body strings that downstream TTS will read aloud. `UI_LANG` (from `get_ui_lang()`) is the *operator* language — used for `print()` messages in `shamanic_pipeline.py`, `shamanic_ai.py`, `shamanic_voice.py`, `generate_report.py`, `generate_md.py`, and `generate_diagnostic.py`, plus all *structural* labels in the diagnostic report. **The notebook stdout is not routed through `UI_LANG`** — it is hardcoded Russian (see *Notebook localization scope* below). Convention for the standalone scripts: `print()` ≡ `t(UI_LANG, ...)`, artefact writes ≡ `t(corpus_lang, ...)`. The shamanic LLM body (Katla/Vieno/Lumi/Sami) is generated in `corpus_lang` via prompt parameters, not via `t()`.

**Notebook localization scope.** The notebook stdout is **not** localized: every `print()` — section headers, the `cell_summary` report, the `cell_qa_rag` greeting, and all per-step diagnostics — is hardcoded Russian. The only `t()` call anywhere in the notebook is `t(LANG, "theses.filename")` (the corpus-language theses filename, from `artifacts.yaml`). A v1.1 experiment that routed section headers and `cell_summary` through `t(UI_LANG, "notebook.*")` was **reverted in v1.1.3** (commit `1edea0c`); `dictionaries/{lang}/notebook.yaml` no longer exists. The notebook is a developer-facing tool — the user-facing localized artefact is the diagnostic report (`generate_diagnostic.py`), not the notebook stdout. Do not re-introduce `UI_LANG` into the notebook without first re-creating the `notebook.yaml` bundles. (Note: `get_ui_lang`'s docstring still lists the notebook among its consumers — that line is stale.)

### Sentiment as optional shamanic feed (implemented)

**Producer — `cell_sentiment` (notebook, optional).** Gated by `ENABLE_SENTIMENT` (parsed from `config.json`'s `enable_sentiment`, default `false`, in `cell_corpus`). When on, it loads `cardiffnlp/twitter-xlm-roberta-base-sentiment` via `transformers.pipeline("sentiment-analysis", truncation=True, max_length=512)`, scores **each paragraph** (`paragraphs` × `para_langs`, the final re-segmented lists), normalizes labels to `negative`/`neutral`/`positive` (handles both the `negative/...` and `LABEL_0/1/2` formats), and writes **raw, unfiltered** rows to `export_results/<project_dir>/sentiment.csv` (`para_id` 1-based, `label`, `score`, `lang`; failed paragraphs get `label="error"`). No confidence floor, no outlier exclusion. On any load failure (missing `transformers`/`torch`, or any of `sentencepiece`/`protobuf`/`tiktoken` needed to build the XLM-RoBERTa tokenizer, or no network) it prints a Russian warning and skips — **no English-model fallback**, `sentiment.csv` is simply not written. Placed between `cell_topics` and `cell_export`; self-contained (writes its own CSV, not via `cell_export`). Both `cell_sentiment` and `md_sentiment` are excluded from `generate_report.py` (`_is_sentiment_cell` → `continue`) so no sentiment verdict reaches the reader-mode artefact. **CPU cost:** on CPU the pass is heavy — empirically comparable to local Whisper speech-to-text on CPU — so on older/thermally-constrained machines it is a real sustained-load strain on the processor (another reason it is opt-in).

**Consumers (two, both keyed off "does `sentiment.csv` exist and have rows?"):**
- **Local, offline — `ritual_emotional_undertow` in `shamanic_pipeline.py`** → `audio_scripts/emotional_undertow.txt`. Walks paragraphs in order, emits one localized mood word per paragraph (`undertow.mood_{negative,neutral,positive}`, 4 per line, uppercased) as an emotional "tide", then a balance summary (`undertow.summary_header` + counts/%). Header `undertow.header` and all mood words live in all six `dictionaries/{lang}/shamanic.yaml`; UI confirmation is `pipeline.ok_undertow`. Absent CSV → ritual returns without writing.
- **LLM — the Vieno branch in `ritual_echoes_of_the_old_world` (`shamanic_ai.py`)**. If `sentiment.csv` has rows, Vieno's prompt = keywords + the per-paragraph sentiment presented as an **emotional arc**, plus an overall distribution line. To respect the gpt-4o **30k-TPM** limit (sending all rows of a long corpus overflows it — a 2579-paragraph book is ~32k tokens → HTTP 429), the body is size-adaptive: ≤ `_SENT_MAX_RAW`=150 paragraphs → full raw rows (`Paragraph N [lang]: label (confidence score)`); above that → downsampled to ≤ `_SENT_SEGMENTS`=40 reading-order segments, each `Paragraphs A-B: dominant (mix: ...)`. The prompt tells Vieno to let the arc shape the chant's dynamics. Without `sentiment.csv` the branch is byte-identical to the original prompt (keywords + 5 raw sentences from `sentences.csv`). The English-prompt / output-in-`LANGUAGE_NAMES[lang]` convention is unchanged. (Measured: the 2579-para book yields a ~1.4k-token Vieno prompt in segmented mode.)

When extending: the `enable_sentiment` flag is mirrored in `config.example.json`/`.ini`; the dependency block (`transformers`+`torch`+`sentencepiece`+`protobuf`+`tiktoken`) is commented out in `requirements.txt`, mirroring the OCR/Icelandic pattern. `_silence_hf_progress()` also quiets the `huggingface_hub` "unauthenticated requests" warning (separate logger from `transformers`).

## HTML report generator

`generate_report.py` reads the saved `.ipynb`, walks `cells`, and emits `export_results/<project_dir>/analysis_report.html` (project dir resolved from `config.json`'s `source_file`, mirroring the notebook's `_slugify`). **The report narrative stays Russian:** `<html lang="ru">` is hardcoded and the notebook's Russian markdown cells are emitted 1:1. A v1.1 experiment that swapped the narrative to `dictionaries/{ui_lang}/narrative.yaml` via a `NARRATIVE_KEYS` map was **reverted in v1.1.3** (commit `1edea0c`); `narrative.yaml` no longer exists, and there is no `NARRATIVE_KEYS` tuple in the current file. `UI_LANG` (`get_ui_lang()`) survives in this script **only** for the operator-facing console prints (`t(UI_LANG, "generate_report.*")` from `reports.yaml`). The one corpus-language substitution in the report body is the theses filename: `тезисы.txt` → `t(target_lang, "theses.filename")`. `cell_qa_rag` is skipped in the report. Key behaviors:

- **Target-language detection** — scans cell stdout for `Выбран язык: ... (xx)` and uses `xx` as `target_lang` (the *corpus* language; defaults to `ru` if not found). The `<html>` `lang` is the hardcoded `ru` (not `UI_LANG`); foreign-corpus content gets per-fragment `<span lang="target_lang">`. The per-fragment target-lang pass is **skipped when `target_lang` is `ru` or `en`** — in a Russian corpus the rest inherits `<html lang="ru">`, and in an English corpus the EN-hardcoding pass tags it anyway — but the EN-hardcoding pass below always runs regardless of `target_lang`.
- **`tag_target_language` (target-lang patterns)** — a list of regex patterns matches structured output formats (numbered `[1] ...` excerpts, ranked tables, POS tables, lemmatization tables, RAG result rows, etc.) and wraps just the foreign-corpus portion. When extending the pipeline, output formats must match one of these patterns or content will not be tagged. HTML-escaping happens before regex matching, so quotes appear as `&#x27;`/`&quot;` in the patterns.
- **EN hardcoding (`EN_HARDCODE_PATTERNS`)** — runs on every report, regardless of `target_lang`. Wraps in `<span lang="en">` the things that are always English regardless of corpus language: spaCy POS tags (`NOUN`, `VERB`, `ADJ`, …), NER labels (`PER`, `ORG`, `[orgName]`, …), spaCy model identifiers (`pl_core_news_lg`, …), Hugging Face model names (`cardiffnlp/...`, `mideind/...`), spaCy pipeline component names (`tok2vec`, `tagger`, `lemmatizer`, …), ASCII filenames with technical extensions (`.csv`, `.json`, `.html`, `.docx`, `.txt`, `.py`, `.md`), the literal `export_results`, and ISO 639-1 codes inside dict-like outputs. Without this pass NVDA reads `VERB`, `cardiffnlp` etc. with the document-default Russian voice. The pass is order-aware: target-lang wrapping runs first, EN hardcoding runs second using `_apply_outside_spans()` so it never wraps content already inside a span. Markdown narrative gets the same treatment for inline `<code>` and `<pre><code>` blocks (`lang="en"` is added blanket-style to every code element, since narrative code is always English).
- **`REMOVE_NOISE`** (read from `config.json`/`config.ini` key `remove_noise`, default `True`) — the accessibility/reader-mode filter. When `True`: (1) drops Hugging Face/torch loading bars and unauthenticated-request warnings; (2) **truncates** the notebook's per-document diagnostic loops (`cell_tok`/`cell_stop`/`cell_lemma`/`cell_pos`/`cell_ner`) to the first `KEEP_DOCS` (=5) `Документ N` blocks **per section**, replacing the rest with the notebook's own formula `... и ещё N документ(ов) (показаны первые 5)`; (3) truncates long TF-IDF/RAG ranking tables to the first `KEEP_RANK_ROWS` (=10) rows. Truncation, not deletion: lemmatization/POS now appear (shortened) instead of being cut entirely, because a screen-reader user benefits from a few representative examples plus a count. Section boundaries are detected by `_is_section_header` (a non-indented, non-`Документ` line) so a cell with several per-document loops (e.g. `cell_tok`'s `Словесные токены:` + `Предложения:`) is trimmed in each section independently and trailing diagnostic sections (`Несогласованные метки NER:` etc.) are preserved. The injected formula is hardcoded Russian on purpose — output-box content is raw Russian notebook stdout, so a `t()`-localized line would read as a foreign sentence mid-block. Set `remove_noise: false` in config for a full diagnostic report.
- **Cell exclusion** — the interactive RAG cell (`md_qa_rag`/`cell_qa_rag`) is the report boundary (detected by content via `_is_qa_rag_boundary` → `break`, since top-level cell IDs are numeric). The optional sentiment cells (`md_sentiment`/`cell_sentiment`) are skipped via `_is_sentiment_cell` → `continue` (they are not the last block) so no sentiment verdict reaches the reader-mode artefact.

When you add a new pipeline step that prints technical English (a new POS tag set, a new HF model id, a new file extension), extend `EN_HARDCODE_PATTERNS`. When you add a new structured output format that wraps corpus content, extend the `patterns` list inside `tag_target_language`.

## Diagnostic report generator

`generate_diagnostic.py` is a **third, independent** report (separate from `generate_report.py`'s reader view and the shamanic TTS artefacts). It reads ONLY the CSV/JSON exports in `export_results/<project_dir>/` (same `_slugify`/`_resolve_project_dir` as the others) and emits `diagnostic_report.html` — a navigable, screen-reader-first structured report: a `<nav>` table of contents plus sections (each its own `<h2>`/`<h3>` + lists) for Overview (counts), Topics (keywords + member paragraph ids, from `topic_keywords.json` + `paragraphs_with_topics.csv`), Theses (`theses.csv`, ranked by score), Named entities grouped by type (`entities.csv`, deduped with frequency counts), and Top keywords (`keywords_tfidf.csv`). Per-section caps (`KEEP_TOPIC_PARAS`/`KEEP_THESES`/`KEEP_ENTITIES_PER_LABEL`/`KEEP_KEYWORDS`) use the localized `diagnostic.more_items` formula. **Why this shape:** the notebook does not export a per-paragraph linguistic breakdown (tokens/POS/NER linked to a paragraph) — `sentences.csv` and `entities.csv` carry no `para_id` — so the report is organised around what the exports actually contain. Localization: structural labels via `t(UI_LANG, "diagnostic.*")` (new `dictionaries/{lang}/diagnostic.yaml`, all six langs); `<html lang="UI_LANG">`; corpus fragments wrapped in `<span lang="CORPUS_LANG">` only when `CORPUS_LANG != UI_LANG` (`detect_corpus_lang()` reads `accessible_text.html`); NER labels always `<span lang="en">`. Run it after the notebook has produced the exports: `python generate_diagnostic.py`.

## Conventions

- All in-notebook narration and prints are Russian; Python comments mix Polish and Russian. Preserve the existing language of any cell you edit.
- Never introduce ANSI colors, emoji, progress bars, or box-drawing characters into stdout — the entire project's value is screen-reader cleanliness. The Hugging Face/tqdm/transformers mute pattern lives in `cell_model._silence_hf_progress()` (used when loading IceBERT/MIM-GOLD-22 for Icelandic); replicate it for any new model loads.
- The `_lg` spaCy models are a hard requirement for `cell_topics` to do anything; the cell self-skips on missing vectors, so partial pipelines are valid but lose topic modeling.
- Notebook cells are edited through the **jupytext pairing** (`accessible_text_analyst.py`, `py:percent`) — see "Editing notebook cells (jupytext)" above. Edit the `.py`, `jupytext --sync`, re-execute. Do not hand-edit the notebook JSON, and do not resurrect the old `.claude_patches/` OLD→NEW patch scripts (now archived under `.claude_patches/_archive_pre_jupytext/`; the folder is gitignored).
- `export_results/` and `.claude_patches/` are gitignored — generated artefacts and local tooling only. The paired `accessible_text_analyst.py` **is committed** (clean reviewable diffs; the `.ipynb` is committed in parallel with outputs stripped by nbstripout). Before committing, run `jupytext --sync` so the `.py` and `.ipynb` don't drift. All generated HTML/Markdown reports live inside `export_results/<project_dir>/`, so no `*.html` or `gemini_notebook_report.md` rule is needed at the repo root.
- **Config loading convention.** Every loader in the codebase (notebook `cell_corpus`, `generate_report.py`, `generate_md.py`, `shamanic_pipeline.py`, `shamanic_ai.py`, `shamanic_voice.py`) probes `config.json` first, then `config.ini`. Both filenames are gitignored. The content is always JSON — `.ini` is purely a Windows usability concession. When adding a new top-level script that needs the config, replicate the same probe order rather than hard-coding `config.json`.
- **JSON path syntax.** Windows paths in `source_file` and regexes in `custom_patterns` must use forward slashes or doubled backslashes (`"C:/Users/foo/doc.pdf"` or `"C:\\Users\\foo\\doc.pdf"`; `"\\d{4}"`, not `"\d{4}"`). JSON has no raw-string syntax. The user-facing README repeats this — keep the warning in sync if the example files change.
- **i18n release scope (as of v1.2).** README is internationalized across `en/pl/ru/fi/is/it`. The standalone scripts' **console output** and the **diagnostic report** (`generate_diagnostic.py`) are localized via `UI_LANG`. The **notebook stdout**, the **`analysis_report.html` narrative** (both reverted to Russian-only in v1.1.3), and this CLAUDE.md are intentionally not translated — see `release_notes.md`. When editing prints in `cell_*` or in the shamanic modules, preserve the existing language to avoid mixing dialects mid-cell.
